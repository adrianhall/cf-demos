# Tasks — What This Demo Teaches

## What This Demonstrates

- **Workers + D1 for per-user relational data.** Every task belongs to exactly one user and is looked up, listed, updated, and deleted by that ownership relationship. That is a relational access pattern — filter and join on a foreign key — rather than a key-value lookup, which is why this demo reaches for D1 (SQLite semantics, a real `WHERE user_id = ?` predicate, and a single `todos` table indexed on `user_id`) instead of Workers KV. See [Choose a data or storage product](https://developers.cloudflare.com/workers/platform/storage-options/) for the same trade-off applied generally.
- **Cloudflare Access as the sole identity provider, with no application login system.** The entire hostname sits behind one Access application with an allow policy that accepts any authenticated identity from the configured identity provider. The Worker never implements sign-up, sign-in, sessions, or password storage — Access supplies a verified identity on every request instead.
- **Deriving a stable owner key from an unvalidated-audience Access identity, and why that is a deliberate simplification.** `cloudflareAccess()` validates the request's Cloudflare Access JWT for the configured team domain but is intentionally configured without pinning this application's `audience`. Because every Access application in a Zero Trust team shares the same JWKS, a valid JWT proves only that some application in the team issued it, not that it was issued for this one. A production system would either pin the audience or add an application-level check (as `demos/url-shortener` does by comparing the identity to an allow-listed email). This demo skips both: it derives `user_id` directly from the verified identity's email and relies on per-row ownership predicates in D1 to keep data isolated, accepting that a valid token from a *different* application in the same team would still be treated as an authenticated user here. That trade-off is safe for this demo because the only consequence of a cross-application token is being treated as an authenticated task owner, not privilege escalation into an administrative capability — unlike the url-shortener's admin routes, there is no elevated role to protect.
- **Ownership enforced in the query, not in a separate store per user.** All users' tasks live in the same `todos` table. Isolation is a property of every SQL statement's `WHERE user_id = ?` clause, not of physical separation — a design choice worth contrasting with, for example, provisioning one KV namespace or Durable Object per tenant.

## How It Works

### Data model

`migrations/0001_create_todos.sql` defines a single table:

```sql
CREATE TABLE todos (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL,
  title TEXT NOT NULL,
  completed INTEGER NOT NULL DEFAULT 0 CHECK (completed IN (0, 1)),
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE INDEX todos_user_id_idx ON todos (user_id);
```

`id` is a client-opaque UUID generated by the Worker (`crypto.randomUUID()`), never derived from user input. `user_id` holds the verified Access identity's email. The index on `user_id` keeps the per-user list and ownership-check queries efficient as the table grows across all users. Wrangler owns this schema through `db:migrate:local` and `db:migrate:remote` (see README.md); Terraform owns only the `cloudflare_d1_database` resource itself.

### Routing and the Access model

Unlike `demos/url-shortener`, there is only one Access application (`infra/access.tf`) and it covers the whole hostname with an `allow` policy for `everyone` — meaning any authenticated identity from the configured identity provider, not an unauthenticated bypass. There is no public route on this hostname: every page and every API request requires a verified Access session.

Because Access enforces this at the edge, the SPA shell itself needs no server-side gate — it is served by the `ASSETS` binding's `single-page-application` fallback like any static file, and `wrangler.jsonc.tpl`'s `run_worker_first` lists only `/api/*`. `src/worker/index.ts` applies `accessMiddleware` (`src/worker/middleware/access.ts`, wrapping `cloudflareAccess()`) to every `/api/*` route before mounting the `/api/me` and `/api/todos` sub-routers, independently re-validating the JWT for API traffic rather than trusting that Access already checked it once for the page load.

`src/access-policies.ts` defines one shared array of path policies consumed by both the Worker middleware and, in local development, `@adrianhall/cloudflare-toolkit/vite`'s `cloudflareAccessPlugin()` (configured in `vite.config.ts`). The same array documents, in one place, that every path on the hostname requires authentication — there is no unauthenticated branch to keep in sync across two configuration surfaces.

### Ownership scoping in queries

`src/worker/todos/repository.ts` is the only code that talks to D1. Every method takes the verified `userId` (the Access identity's email, read from `context.get("Cloudflare_Access_Identity").email` in `src/worker/routes/todos.ts`) as its first argument and includes it in the SQL predicate:

- `list(userId)` — `SELECT ... WHERE user_id = ?`
- `create(userId, input)` — inserts a new row with that `user_id`
- `update(userId, id, input)` / `delete(userId, id)` — first reads the row with `WHERE id = ? AND user_id = ?`, returning a `404` if it does not match, then mutates with the same compound predicate
- `deleteCompleted(userId)` — `DELETE ... WHERE user_id = ? AND completed = 1`

No route ever accepts a `user_id` from the request body or query string — it is always the value Access verified for that request. This is what makes it structurally impossible for one signed-in user's request to read or mutate another user's row, even though every user's data lives in the same table.

### Observability

`cloudflareLogger()` provides request-scoped structured logging. `src/worker/routes/todos.ts` emits one informational event per successful mutation — `todo_created`, `todo_setstate`, `todo_removed`, or `completed_todos_removed` — placed after the Access and validation guards so a log entry only ever reflects a real, authorized change. Each event carries only the task's UUID (and, for `todo_setstate`, the new `completed` value), never the task's title or any identity data. Terraform enables Workers Logs at 100% sampling and traces at 10% sampling on the Worker resource.
